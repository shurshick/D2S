# HTTP Probe Fidelity: аудит и ограниченная сравнительная диагностика

## Исходное состояние и источники

Работа начата с чистого main `8ce411883f2d925d836f68829accaa180a4a767c`,
совпадавшего с origin/main; исходники v0.5.1 —
`f49938564b0ade9755a3c73a1ab2d5f9b8731891`.
REA недоступен; действует ранее данное пользователем разрешение на обычный
разбор исходников и собственные тесты. Сторонняя реализация не копировалась.

Идея сравнения диагностического HTTP и навигации проверена по
[Ladon v3.2.0](https://github.com/belotserkovtsev/Ladon/releases/tag/v3.2.0),
commit `babbcc0b281fc64d1c37b0d72fcf3669f8eb4084`, и его
[methodology](https://github.com/belotserkovtsev/Ladon/blob/babbcc0b281fc64d1c37b0d72fcf3669f8eb4084/docs/methodology.md).
Ladon меняет также TLS-отпечаток; в D2S эта часть не переносится.

## Что установлено

`request_page_budget()` действительно отправлял Mozilla/5.0, Accept: */*,
Accept-Encoding: identity (либо gzip/gzip, deflate в специальных измерениях),
Connection: keep-alive. Свой TLS-клиент завершает TLS 1.2/1.3; он не является
Chrome, не воспроизводит HTTP/2 и не проверяет доверенную цепочку сертификата.
Совпадение SAN фиксируется отдельно и не заменяет проверку подлинности.

Reader различает корректный короткий ответ, недочитанный Content-Length,
незавершённый chunked, тело до EOF и неоднозначный framing. Размер chunked —
байты тела без обрамления; ожидаемый размер неизвестен до завершения. У gzip
считаются сжатые байты, распаковки здесь нет. Сигнатуры блокировки ищутся в
ограниченном несжатом префиксе. cf-mitigated: challenge даёт CHALLENGE.
200/прочие 2xx и 304 классифицируются положительно; 451 — юридический отказ;
403/429/5xx без явной сигнатуры блокировки — нейтрально. Переадресация на
известный портал блокировки отличается от обычного Location.

Воспроизведена неоднозначность: полный нейтральный 403/3 байта в старом
request_page_budget получает APPLICATION — доказательство завершения HTTP,
**не** эквивалент загрузки страницы браузером. В sched.c полный ответ,
исполнение плана на потоке, packet budget, ECH и anti-bot проверяются разными
ветками. В volume.c объёмный вывод требует 2xx, корректного framing,
минимального объёма и парных измерений; короткого 403 недостаточно для вывода
о большом потоке. Полевой дефект автоматического подтверждения стратегии
этим опытом не доказан. Поэтому правила контроллера и фоновые запросы сохранены.

Рабочий режим следует ограниченному числу редиректов того же имени;
завершённый внешний HTTPS redirect имеет отдельное пояснение: его цель не
проверялась. Существующий scanner ресурсов и объёмный измеритель сохранены.
Дополнительный обход ресурсов в новой диагностике намеренно не добавлен.

## Новый режим

```
d2sfetch --compare-http --name example.org --ip 203.0.113.10 --deadline 3000
```

Адрес в примере заменить настоящим. --ip фиксирует один адрес для обоих
измерений; без него имя разрешается один раз. --tls12 и --wire сохраняются.
Вывод — JSON независимо от --json. --quic, --ladder и --path кроме / отвергаются.
Каждый профиль использует отдельное TCP/TLS-соединение. Сравниваются статус,
тип/число/ожидаемый объём байтов тела, framing, chunked, encoding, полнота,
Location, TLS, уровень доказательства, тип отказа и причина. TLS/соединение могут
не состояться у любого из профилей; его результат всё равно остаётся в отчёте.

Старый HTTP-запрос (рабочий режим и диагностический legacy):

```http
GET / HTTP/1.1
Host: example.org
User-Agent: Mozilla/5.0
Accept: */*
Accept-Encoding: identity
Connection: keep-alive
```

Второй профиль:

```http
GET / HTTP/1.1
Host: example.org
User-Agent: D2S-Probe/1.0 (HTTP navigation diagnostic)
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8
Accept-Language: ru-RU,ru;q=0.9,en-US;q=0.8,en;q=0.7
Sec-Fetch-Dest: document
Sec-Fetch-Mode: navigate
Sec-Fetch-Site: none
Accept-Encoding: identity
Connection: close
```

UA честно обозначает диагностический клиент. Это HTTP-профиль навигации,
а не полный отпечаток Chrome: сервер всё ещё может применить другую политику
по UA/TLS. Client Hints не добавлены. Оба диагностических профиля читают один
ответ, без редиректов и ресурсов, максимум 256 KiB расшифрованного HTTP-потока
(заголовки + тело) и не дольше заданного срока чтения. DNS, TCP и TLS имеют
собственные существующие сроки; --deadline не является общим сроком всей команды.
Лимит чтения явно отмечается local_limit и не становится доказательством обрыва.
Память под всё тело не выделяется.

В диагностике полный нейтральный HTTP-ответ не повышается до APPLICATION.
Явный cf-mitigated и несжатый префикс /cdn-cgi/challenge-platform/ дают CHALLENGE;
это узкая сигнатура, не универсальный распознаватель всех CAPTCHA.
Redirect записывается с HANDSHAKE, целевой ресурс не проверяется.
Рабочая классификация остаётся прежней. Переключатель профиля привязан к потоку,
после сравнения сбрасывается; результаты не поступают планировщику.

## Воспроизводимый пример и проверки

Локальный TLS-сервер выбирает ответ по фактически полученному Accept:

| Профиль | HTTP | Content-Type | Тело / ожидается | Полнота | Уровень |
|---|---:|---|---:|---|---|
| legacy | 403 | text/html | 3 / 3 | полный | HANDSHAKE; HTTP нейтрален |
| navigation | 200 | text/html | 65536 / 65536 | полный | APPLICATION |

Это расхождение политики HTTP-сервера, не диагноз DPI и не проверка Chrome.
Тест воспроизводит разницу на настоящих локальных TLS 1.2 и TLS 1.3 соединениях.

`make -C core test-verify-http test-http-profiles test-d2sfetch-cli`:
26 новых комбинаций профиль/ответ: короткий 200, обрыв Content-Length/chunked,
429/503/451, header/body challenge, redirect того же имени, timeout,
локальный лимит, полный chunked, gzip; дополнительно Accept-зависимый сервер,
истёкший общий срок чтения и отсутствие утечки режима в следующую рабочую пробу.
4 интеграционных TLS/CLI теста и прежние 4 CLI контракта.
Старый набор reader/budget/ECH/HTTP3 тестов сохранён.

## Влияние и границы

Нет дополнительных постоянных запросов, зависимостей продукта и изменений
wire 22 или пользовательского интерфейса. На ручную команду — ровно две пробы,
не больше 512 KiB суммарного расшифрованного чтения, без автоматических повторов.
Метаданные диагностики (104 байта на поток) хранятся отдельно от результата verifier;
его размер на x86_64 сохранён: 2800 байт до и после. Нет роста каждого сохранённого
результата планировщика и новых выделений на пакет;
TLS/HTTP fingerprint браузера и подлинность origin этим не доказываются.
Живые CDN и реальные браузеры в этой задаче не использовались как доказательство.
