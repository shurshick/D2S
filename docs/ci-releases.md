# Проверки и быстрые выпуски

Новая схема относится к следующим выпускам после 0.3.0. Выпуск 0.3.0 завершился на прежней схеме: текущий запуск не отменялся и проверки не сокращались.

## Как выпускать

1. Отправить изменения в main и дождаться зелёного D2S checks.
2. Actions → D2S release, ветка main, новая версия без префикса.
3. При необходимости полной пересборки библиотек включить clean_build.
4. Выпуск создаётся предварительным. После проверки на стенде отметить его стабильным и latest; только тогда его увидит ночное автообновление.

Release план проверяет успешный CI именно выбранного SHA в этом репозитории и для push-события. Другой коммит, чужой fork, PR-проверка и незавершённый/проваленный CI не подходят. Если main изменился во время сборки, публикация остановится; собранные артефакты останутся в Actions.

## Что ускорено

- В release больше не дублируются native core/datapath/detect, Telegram, panel и установочные тесты: они находятся в D2S checks.
- Длинный engine-прогон оставляет маркер успеха только после всех трёх make check. Ключ учитывает Git-деревья core/datapath/detect/runtime, CLI-фикстуру, рецепт CI, версию компилятора, Zig и QEMU.
- README и CSS не меняют этот ключ. Изменение кода движка, его тестов/Makefile или рецепта проверки требует нового полного прогона. При отсутствии кэша выполняются тесты; успешность не предполагается.
- OpenSSL/zlib кэшируются отдельно для ARM64, ARMv7 и MIPSel. Ключ включает архитектуру, pinned исходные версии, Zig, flags, build-target и рецепт сборки. Внутренний stamp и наличие заголовков/статических библиотек проверяются перед повторным использованием.
- Бинарники D2S собираются заново с версией и SHA текущего выпуска. Под QEMU запускаются они и crypto link smoke. Проверки состава, SHA-256, RAM preflight и Ed25519 остались перед публикацией.
- Расширенная матрица upstream с sanitizer-проверками сохранена как отдельный ручной D2S extended audit, чтобы не дублировать каждое обычное изменение.

В кэш не входят ключи, конфигурации роутеров, credentials и каталоги авторизации. Используются точные ключи без restore-keys. Полный clean_build отключает восстановление и использование crypto-кэша.

## Проверка изменений процесса

Локальные policy-тесты проверяют отказ release gate для чужого SHA/fork/PR/неуспеха и отсутствие повторного engine-прогона для README/CSS. Изменение C-кода/CLI-фикстуры/CI-рецепта меняет engine-ключ; dirty engine inputs отвергаются.

actionlint 1.7.12: все три workflow прошли статическую проверку. На реальной локальной ARM64 кросс-сборке OpenSSL/zlib: cold 26 с, warm менее 1 с; QEMU crypto smoke прошёл оба раза. Это не измерение полного GitHub release: в нём остаются установка инструментов, компиляция D2S, QEMU, упаковка и подпись.

Первый CI после смены схемы прогревает кэш. Изменение движка, toolchain или рецепта тоже потребует длинной проверки; публикация уже проверенного коммита её не повторяет.

Справочник GitHub: [dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs).
