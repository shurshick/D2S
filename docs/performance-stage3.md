# Третий этап: ожидание начальной TCP-базы

На стенде начальная база из трёх отрицательных TCP-проб занимала около 18,2 с:
каждая отдельно ждала ответ до 6 с. Теперь эти три полных соединения могут
ожидать ответ одновременно. Это изменение расписания одного вопроса, а не
сокращение числа повторов, таймаутов или критериев успешности.

Оптимизация включена только для предварительной TCP-базы контроллера с
числовым IPv4/IPv6 адресом. CLI по умолчанию остаётся последовательным;
для сравнения предусмотрен `--parallel-base`. Остальные вопросы, свойства,
проверки планов и запасной перебор сохраняют прежнее исполнение. Измеренная
предварительная база затем используется повторно без новых соединений.

Существующий измерительный работник выполняет одну пробу; ещё максимум два
временных потока выполняют остальные. При большем настроенном числе повторов
выполняются следующие группы, повторы не отбрасываются. Внешнее ограничение
числа поисков по загрузке CPU/RAM сохранено. Внутри одного такого поиска теперь
может быть до трёх одновременных базовых соединений вместо одного.

При отказе создания потока выполняются последовательно только ещё не начатые
пробы. Уже отправленное не повторяется; отказ потока не становится сетевой
ошибкой. Все созданные потоки присоединяются до возврата результата. Ошибки
агрегируются по номеру пробы, а не по скорости завершения. Пользовательские
обработчики наблюдений и отмены вызываются только исходным работником.
Отмена прекращает запуск новых групп; уже начатые соединения заканчиваются
в пределах прежних сроков подключения/ответа.

Параллельные попытки меняют временное распределение нагрузки. Совпадение
правил оценки не доказывает одинаковое поведение любой ограничивающей
частоту или меняющейся во времени сети. Поэтому нужны и стендовые сравнения,
и отдельная проверка приложений после установки кандидата.

## Reviewed engine changes

- `detect/classify.c`: ограниченная группа полных базовых проб, сбор результатов,
  последовательный запасной путь при нехватке ресурсов. Ранее принятые изменения
  времени/достаточного ответа из этапа 2 сохранены.
- `detect/bridge.c`: включение только для предварительной TCP-базы контроллера.
- `detect/include/d2s_detect.h`: опция локального расписания; сетевой протокол
  контроллера/датапата не меняется.
- `detect/main.c`: явное включение в диагностическом CLI.
- `detect/test_bridge.c`: проверка опции в мосте контроллера.
- `detect/test_parallel_base.c`, `detect/Makefile`: регрессии и включение в check.

Точные хеши изменённых файлов закреплены в
`tests/keenetic/audited-engine-changes.json`. Неизменённая часть исходной базы
по-прежнему сверяется побайтово. Перехват, PPE, очереди, DNS, Telegram и
WhatsApp этим этапом не переписываются.

## Проверки и границы

Регрессия сначала падала на последовательной реализации. Проверены все
27 комбинаций успеха/тишины/локальной ошибки, порядок выбора ошибки,
отказы создания каждого дополнительного потока, семь повторов несколькими
группами, повторное использование базы, отмена и отсутствие вызовов обработчиков
из дочерних потоков. Реальные IPv4/IPv6 loopback-соединения проверяют совместное
ожидание трёх подключений и положительный/отрицательный ответ.

[Полевое сравнение](field/2026-11-06-performance-stage3.md) показывает выигрыш
на начальном вопросе. Оно не измеряет ускорение всего подбора. Длинный запасной
перебор остаётся: проверка вариантов не обнаружила одинаковых скомпилированных
планов, которые можно было бы безопасно выбросить. Telegram Web отдельно
остаётся нерешённой задачей.
