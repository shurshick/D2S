# WhatsApp: ECH + TCP Timestamp не наследовал подтверждённый план

## Поле и границы вывода

08.11.2026, основной Keenetic, работающие d2sd/d2sc d2s-v0.5.1, wire22.
Владелец воспроизвёл зависание приложения WhatsApp на подключении; затем
страница могла открываться без оформления. Свежий отдельный браузер и curl
через тот же шлюз получали страницу и полный CSS (~575 КБ).
Это не опровергает ошибку на другом TLS-профиле приложения.

В журнале контроллера static.whatsapp.net/web.whatsapp.com: план подтверждён,
но к потоку не применён; повторный поиск не начинается. В каталоге присутствуют
как старые общие TLS-записи (tcp_profile=0), так и новые TS-записи (tcp_profile=2).
Ограниченный захват только соединений этого ПК к двум адресам WhatsApp показал:
QUIC передаёт данные страницы, TCP к серверу статики повторяет отправку и
закрывается. Дополнительный захват подтвердил полный ClientHello с SNI
static.whatsapp.net, extension ECH и TCP Timestamp; в одном соединении сервер
не передал прикладной нагрузки, в другом были ответные TLS-байты. Это не
доказательство успешной загрузки ресурса во втором соединении.
PCAP, резервные копии и данные приложения остаются приватными вне git.

Браузерный профиль из предыдущей задачи не устанавливался на роутер и эту
ошибку не исправлял. Сброс авторизации, кэша, firewall или маршрутов не делался.
Попытки временного логирования WebView2 заблокированы Windows; проверено,
что диагностического registry value не появилось. Приложение возвращено к
обычному запуску. tcpdump/libpcap были установлены только для захвата и удалены;
временные файлы захвата на роутере удалены после сохранения на ПК.

## Причина

В plans.c modern_shape_for_ech() и shape_fits() уже различали варианты
ECH_NO_TS/ECH_TS, но три места выбора fallback проверяли только старую
ECH_TCP. Поэтому:

- старая общая запись могла оказаться первой h.any и закрыть путь к
  существующему точному ordinary TLS+Timestamp плану;
- пробный план подходящего локального порта не наследовался ECH_TS/NO_TS;
- адресный ordinary TLS-план не наследовался этими ECH-вариантами.

Контроллер при этом знал совместимую подтверждённую привязку и не запускал
подбор для потока, на котором датапат отказался её выбрать. Это объясняет
зафиксированное расхождение, но устранение всех симптомов WhatsApp ещё
требует проверки установленного исправления на устройстве.

## Минимальное исправление

shape_is_ech_tcp() распознаёт все три ECH-варианта. В трёх прежних местах
fallback применяется уже существующий modern_shape_for_ech():
ECH_TCP → MODERN, ECH_NO_TS → MODERN_NO_TS, ECH_TS → MODERN_TS.

Не ослабляется сравнение Timestamp. Не используются общие записи вместо
известного профиля. Сохраняются приоритет точного ECH, пробного порта,
постоянной записи, адреса и suffix/bypass. Wire22 и все ID не меняются.
Исполнитель пакетов, стратегии, firewall, DNS и Telegram не менялись.

## Проверки

Новый тест в test_plans.c до правки давал 12 FAIL: name/probe/address ×
TS/NO_TS × IPv4/IPv6. После правки PASS, включая отказ для противоположного
Timestamp-профиля и приоритет отдельного ECH-плана.

- Полный make -C datapath check — PASS.
- Новый и прежний test_plans под ASan/UBSan — PASS.
- HTTP runtime/live и UDP runtime (136 full-packet cases) — PASS.
- 144000 прежних детерминированных lookup: исходы и метаданные совпали,
  ASan/UBSan — PASS. Это старое покрытие не включало новый ECH+Timestamp
  сценарий; оно не доказывало отсутствие этого дефекта.
- ARM64, ARMv7, MIPSel, MIPS BE, amd64: полная линковка d2sd и test_plans,
  исполнение проверок под QEMU/нативно с assertions — PASS.

Дифференциальный runner теперь берёт test_plans.c из указанного baseline для
обоих вариантов. Новые намеренно исправляющие поведение регрессии запускаются
отдельно текущим make check: они закономерно не проходят на старом коде.
Так историческое сравнение не смешивается с новыми требованиями.

## Полевая установка и результат

Владелец явно разрешил установку на основном 192.168.1.1 с коротким
перезапуском D2S. Перед записью сохранены исходный d2sd, config и catalog;
backup на роутере: /opt/d2s/wa-ech-backup-20261108 (доступ root), копия на ПК
приватная. Подменялся только /opt/sbin/d2sd атомарным rename.
Использована штатная команда engine-restart: Telegram PID остался прежним.

Первый кандидат d2s-v0.5.1-wa-ech-test1 был отвергнут контроллером: handshake
требует одинакового release ID, не только wire22. Немедленно восстановлен
исходный бинарник и штатный движок, затем исправление пересобрано с общим
release ID d2s-v0.5.1. Новую сборку различаем по SHA256, а не номеру в панели.
Это локальный hotfix, не новый подписанный выпуск. Релизный конвейер не менялся.

- Исходный d2sd: 05a8ec8bf4fa8899a7dda87c9ad9c8c83dcb3c2f0231b78ba45a2ec1b908c808.
- Установленный исправленный d2sd: 4f58323affd922ccf536382462e8fda7cb0e56f600ae0a30df9af4bf6c9d7674.
- На самом роутере self-check=ok; хеш /proc/PID/exe совпал с установленным
  исправлением. Обе heartbeat подтвердили connected/ready/external = 1/1/1,
  PID стабильны, wire22, очередь2000 привязана, правила и PPE 8/8 восстановлены.
- Конфигурация byte-exact совпала с резервной копией; все 46 уникальных plan_id
  из исходного каталога присутствуют после установки. Каталог не очищался.
- Три полных закрытия/запуска WhatsApp подряд: наблюдались нормальное оформление
  и список чатов. До установки воспроизводились зависание и отсутствие CSS.
  Отправку сообщений/файлов и звонки в этом опыте не выполняли.
- Изменений браузерной политики, сброса кэша/авторизации нет. Диагностические
  tcpdump/libpcap и временные файлы захвата с роутера удалены.

Исходник исправления: коммит 4c1d7c9. Не было push, тега или публикации релиза.
Долговременная устойчивость за пределами трёх запусков этим опытом не доказана.
