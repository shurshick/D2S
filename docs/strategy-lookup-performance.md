# Strategy Lookup Performance — измерение и решение

Этот отчёт фиксирует завершение benchmark-задачи. Последующее отдельное
исправление ECH/Timestamp описано в [WhatsApp audit](whatsapp-ech-timestamp.md).

## Итог

Рабочие `datapath/plans.c`, `session.c` и `include/d2s_plans.h` оставлены
**байт в байт исходными**. Добавлены воспроизводимые измерения и сравнительные
регрессии. Хеш-фильтр проверен, но не включён: он ускоряет плотные группы имён
одинаковой длины с общим префиксом, а на малых разреженных группах добавляет
работу. Стабильный выигрыш CPU на обычном трафике роутера не доказан.
Сложный индекс ради этого не вводился. Это намеренный результат задания,
а не незавершённая оптимизация.

Начальный чистый HEAD: `8ce411883f2d925d836f68829accaa180a4a767c`, origin/main
на момент начала. HTTP-часть — отдельный коммит
`3af9cfec92d55ab0ce76490fb7f00b41d8fce12e`:
[полный аудит HTTP](http-probe-fidelity.md).
Релизов, тегов, развёртывания и сетевых изменений в этой задаче нет.

## Аудит порядка поиска

Изучены `plans.c`, его публичный API, вызовы из `session.c` и прежние tests.
Источник идеи: [zapret2 dp_match](https://github.com/bol-van/zapret2/blob/9b9b929f837978173d787a5773a47a91d90f7f81/nfq2/desync.c),
commit `9b9b929f837978173d787a5773a47a91d90f7f81`.
Использован принцип дешёвого раннего отбрасывания, код донора не переносился.
REA недоступен; действует ранее данное разрешение пользователя на обычный разбор.

D2S уже отбрасывает вид ключа, family, форму и пробный порт до сравнения имени
в find_name_shape_port/find_name_port; name_eq сначала проверяет длину.
scan_addr проверяет kind/family до memcmp. scan_name объединяет категории
shaped/modern/grandfather/any в один проход `v[0..used)`, а не по всей ёмкости.
В session.c сначала разбираются протокол и контекст потока; fwmark и порт назначения
не являются произвольными дополнительными фильтрами существующего ключа таблицы.
Добавлять их ради сходства с другим проектом было бы изменением семантики.

`any` нельзя выбросить по несовпадению transport/shape/Timestamp: известное имя
с неподходящей формой в ряде случаев должно запретить подстановку адресного
плана соседа CDN. Отдельны исключения для QUIC и ECH. Проба точного локального
порта имеет приоритет перед постоянным планом; точное имя сильнее BYPASS;
BYPASS снимает наследование суффикса, а не собственный план имени.
Подмена этих правил ранними фильтрами была бы ошибкой.

Lookup вызывается при выборе плана в контексте соединения и разборе приветствия;
это не доказательство такого же расхода на каждый байт всего трафика.
Изолированный benchmark не заменяет профиль CPU реального роутера.

## Методика

Linux / Ubuntu 24.04 / WSL2 6.6.87.2, x86_64, AMD Ryzen 7 9700X, GCC 13.3.0.
`-std=c99 -O2 -Wall -Wextra -Werror`, assertions включены, один logical CPU 15.
Финальные серии выполнены после завершения параллельных сборок.
Размеры 32, 128, 256, 512, 1024, 2048; во всех таблицах used == capacity.
Два набора: похожие имена одного размера и разные имена/длины с ранним отказом.
В обоих есть IPv4/IPv6, адреса, несколько форм одного имени, Timestamp,
суффикс, исключение и временный план своего порта.

14 случаев на размер/набор: exact4/exact6, name miss, address4/address6,
address miss4/miss6, Timestamp match/mismatch, suffix, bypass, trial hit,
trial miss с возвратом permanent и ECH fallback. По пять независимых запусков,
101 серия по 64 lookup, прогрев 128 вызовов. Средние и CPU ns — на один lookup;
median/p95/p99 — распределение средних серий. Дополнительно сохранены
`lookup_*_raw_ns`: median/p95/p99 для 1025 индивидуальных обращений с ценой
двух обращений к часам. Они не выдаются за чистое время самого matcher.
Пропусков и выбросов вручную не удаляли.

Посещённые записи измерены отдельным инструментированным бинарником,
не тем, которым измерялось время. Учтены основной каталог, suffix/bypass и
flow-probe scans. В продукте счётчиков нет. Нет выделений памяти на lookup.
RSS — ru_maxrss всего процесса, не сумма выделений одного каталога.
`table_bytes` учитывает основные/пробные слоты и фиксированные области;
`plan_bytes` — sizeof минимальных тестовых объектов планов, не все возможные
payload настоящих стратегий.

## Проверенный, но отклонённый вариант

В `bench/lookup-hash-experiment.patch` сохранён собственный эксперимент:
32-битный ASCII-folded FNV-фильтр в padding entry, раннее исключение HTTP/длины,
отложенное вычисление query hash в scan_name. Первое проверенное равенство
позволяет взять уже вычисленный хеш записи. После совпадения хеша обязательно
выполняется полное name_eq; хеш не является идентификатором плана.
В эксперименте затрагивались только entry, name_hash, scan_name и заполнение
имени в set_name_family. Ни индекс, ни новые выделения на пакете не нужны;
entry оставалась 304 байта на x86_64.

На плотных похожих именах выигрыш большой и повторяемый. На разреженных
группах постоянная цена фильтра может перевесить выгоду: например name_miss
при 32 записях в varied_names. Изменение частоты процессора/планировщика даёт
заметный разброс даже на одинаковом исходнике. Переносить лучший коэффициент
на общий CPU или скорость приложений было бы неправильно. При типичных
малых каталогах не получено устойчивого основания менять рабочую реализацию.
Индекс и постоянные таблицы дополнительных счётчиков не внедрялись.

## Регрессии

`test_plans_differential.c` выполняется против исходной и испытуемой реализации
в разных бинарниках. Он проверяет настоящую коллизию FNV:
`c740766d21d73.test` и `c0d5dbf0fc04e.test` → `0x22bdd4c5`, разный регистр,
близкое отсутствующее имя, IPv4/IPv6, Timestamp, пробный/постоянный приоритет,
точный план против BYPASS, suffix/исключение, очистку проб, replacement,
генерацию привязки, удаление, LRU с уплотнением и истечение flow-probe.
Подтверждённые постоянные записи не имеют придуманного TTL.

Дополнительно: 36 000 детерминированных шагов установки/замены/удаления,
изменений suffix/bypass и очистки проб на шести ёмкостях, по четыре обращения
на шаг. Сравниваются 144 000 строк: plan_id, generation, kind/family/shape,
temporary, trial ownership, used и shape_misses. Полный прежний test_plans
также исполняется против обеих реализаций. Финальный исходник совпадает с
baseline по SHA-256; эксперимент тоже прошёл этот сравнительный тест с ASan/UBSan.
Никакого execution_id или wire-поля эти изменения не затрагивают.

Трасса обоих вариантов: SHA-256
`4761ae7f89b109f6a4374404e4ab0e46498f1c4c84cc87a5f209000321ba1e4a`.
[Эксперимент](bench/lookup-hash-differential.json),
[итог](bench/lookup-final-differential.json).

## Воспроизведение

На Linux/WSL, из корня git-репозитория (Python 3 и C compiler; только тестовые
инструменты, зависимостей продукта не добавляют):

```sh
python3 scripts/benchmark-plans.py --ref 8ce411883f2d925d836f68829accaa180a4a767c --out /tmp/d2s-before.json
python3 scripts/benchmark-plans.py --out /tmp/d2s-after.json
python3 scripts/test-plan-lookup-differential.py --sanitize --out /tmp/d2s-differential.json
```

Процесс автоматически закрепляется за первым доступным CPU; для другой
свободной логической нити есть --cpu N. Не сравнивать серии на разных платформах.
Для сохранённого эксперимента, не меняя рабочую копию:

```sh
git show 8ce4118:datapath/plans.c > /tmp/d2s-hash.c
patch /tmp/d2s-hash.c < docs/bench/lookup-hash-experiment.patch
python3 scripts/benchmark-plans.py --source /tmp/d2s-hash.c --out /tmp/d2s-hash-bench.json
python3 scripts/test-plan-lookup-differential.py --candidate /tmp/d2s-hash.c --sanitize
```

[Исходные замеры](bench/lookup-before.json),
[отклонённый фильтр](bench/lookup-hash-experiment.json),
[итоговые замеры](bench/lookup-after.json): по 840 строк, все серии сохранены.

## Общие проверки обеих частей

- `make -C core -j4 check` — PASS (ZIG переопределён реальным локальным путём).
- `make -C datapath -j4 check`, `make -C detect -j4 check` — PASS.
- HTTP reader и новые 26 профильных комбинаций — ASan/UBSan PASS.
  GCC -O1 видит существующее format-truncation предупреждение в неизменённом
  HTTP/3 snprintf; только оно не делалось фатальным для этого sanitizer harness.
  Обычные -O2 сборки прошли с -Werror. Ошибок памяти/UB не было.
- Два локальных TLS-профиля через настоящие TLS 1.2/1.3 и CLI — PASS.
- Исходный/экспериментальный и исходный/итоговый matcher: прежние тесты и
  144 000 сравнений, ASan/UBSan — PASS.
- ARM64, ARMv7, MIPS little-endian, MIPS big-endian, x86_64 musl:
  d2sc + d2sfetch + d2sd/planlab/ctlprobe слинкованы Zig 0.16; новые HTTP
  профили (`test_verify_http --profiles-only`), прежний test_plans и новый
  test_plans_differential исполнены под соответствующим QEMU (x86_64 нативно).
  Assertions принудительно включены -UNDEBUG. d2sd --version показывает wire=22.
  Для локальной линковки Zig C units сначала переводились в object перед
  архивом; релизный конвейер не менялся. Полный старый reader набор под QEMU
  не использовался как гейт: его односекундные фикстуры слишком коротки для
  побайтовой эмуляции. Нативный полный набор прошёл.
- Pinned network guard: 198 исходных файлов совпали; 77 ранее/сейчас
  проверенных изменений совпали с сохранёнными хешами. Python syntax и diff check — PASS.

Это проверки сборки, локального TLS и кода. Измерения CPU/RAM на физическом
роутере и полевое подтверждение Chrome не проводились. Другие архитектуры
из расширенной таблицы build-target.sh в этой задаче не собирались.

## Оставшиеся границы

HTTP-профиль не воспроизводит Chrome TLS/HTTP2, не выполняет JavaScript,
не определяет все антиботы и не удостоверяет origin. Диагностика ограничена
корневым документом: загрузка дополнительных ресурсов отдельно не добавлена.
Отказ HTTP и различие профилей не равны DPI. Существующая рабочая логика
подтверждения и объёмных измерений сохранена.

В matcher линейная стоимость больших каталогов осталась. Если полевой
профиль покажет её заметную долю CPU, следующий шаг — измерение конкретных
распределений family/name length/shape, затем оценка компактного индекса.
На основании одного удачного синтетического сценария индекс не оправдан.

Не изменялись NFQUEUE recovery, firewall, startup, Telegram/WhatsApp,
QUIC-стратегии, протокол 22, идентификаторы, релизный конвейер и подписи.
Конфигурации роутеров и сохранённые планы не трогались.
