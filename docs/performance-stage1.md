# Ускорение подбора: первый этап

Основа — D2S 0.3.0, исходный commit `8cb2151`. Изменения не меняют правила
включения трафика, PPE-окна, обнаружение блокировки, набор воздействий,
таймауты сетевых проб или критерии подтверждения результата.

## Что изменено

- Контроллер вычисляет ближайший срок планировщика перед `poll()`: выпуск
  очереди через 250 мс, резервное ожидание установки кандидата 50 мс,
  проверка результата и отложенная RX-проверка. ACK и завершение рабочего
  потока по-прежнему будят цикл. В простое остаётся прежний интервал
  обслуживания 3 секунды; активного опроса готового состояния нет.
- Снимок ресурсов снимается с исходным интервалом 1 с при наличии спроса на
  замеры. Пороги CPU/RAM/conntrack и принцип AIMD сохранены.
- Журнал итога и диагностический JSON содержат `classify_ms`, `contact_ms`,
  `verify_ms`: суммарное монотонное время рабочих потоков соответствующих
  этапов, включая сетевые ожидания. Классификация включает базу, объём и
  приостановку QUIC; это не CPU-время. Эти числа нельзя безусловно вычитать
  из общего времени, когда задача была отменена или ещё завершала поток.
- Кэш WhatsApp хранит проверенную пару «точное имя — адрес» на прежние 6 ч.
  Новое имя не инвалидирует действительные результаты остальных имён.
  Неудача пары получает паузу в один исходный интервал обработки (30 с).
  Успешные пары сохраняются независимо от неудач других имён; запись NDM
  сохраняется после всех выполненных изменений, включая частичный успех.
  Кэш очищается от пар вне текущего списка имён/адресов.
- Обработчик WhatsApp просыпается при атомарном обновлении файла наблюдаемых
  DNS-имён через inotify. Сравнение токена после установки наблюдения не
  теряет изменение, случившееся во время предыдущей обработки. Период 30 с
  остаётся страховкой для пропущенных событий и имён, найденных в журнале.
  При недоступности inotify или старой версии наблюдателя используется
  прежнее ожидание. Дополнительная служба и пакет не нужны.

## Reviewed engine changes

Побайтовая проверка происхождения сохранена. Обоснованные изменения базы
перечислены с точными SHA-256 в
`tests/keenetic/audited-engine-changes.json`; остальные файлы по-прежнему
сверяются с исходной базой после нормализации пространства имён.

- `core/d2sc.c`: срок `poll()` и запуск обслуживания по ближайшему сроку.
- `core/sched.c`, `core/include/d2s_sched.h`: вычисление срока, пробуждение
  следующей порции собственных планов, сброс уже использованного срока RX,
  измерение времени рабочих потоков и публикация итогов.
- `core/diagnostics.c`, `core/include/d2s_diagnostics.h`: дополнительные
  поля диагностики без изменения смысла вердикта.
- `core/test_diagnostics.c`: проверка точной сериализации новых полей.

## Проверки

Регрессия таймеров воспроизводит прежнее ожидание 3000 мс вместо сроков
50/250/500 мс. Проверяет занятый лимит, отсутствие опроса в простое и
отсутствие цикла при локальном отказе выделения/отправки.

Регрессии WhatsApp воспроизводят повторные TLS-пробы старого имени при
новом имени и потерю обработки остальных имён после одной неудачи.
Проверяются срок отрицательного кэша, сохранение старых записей при
неудачной замене и запрет присваивать пользовательские DNS-записи.
Реальные файловые события проверяются отдельным CLI-тестом, в том числе
изменение до начала ожидания, посторонние файлы, первый файл и завершение
планировщика вместе с ожидающим процессом.

Поле: только стенд 192.168.31.1, keenetic-doq сохраняется. Успех сайта за
шлюзом с собственным обходом не доказывает работу обхода стенда.
Увеличение параллелизма, перестановка вопросов, новые сетевые воздействия
и изменение универсальных таймаутов в этот этап не входят: сначала нужны
данные новой диагностики и отдельная проверка каждого изменения.
